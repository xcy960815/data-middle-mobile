# 决策门槛

需求已明确、影响范围可验证且不改变对外契约时可以直接执行；否则说明影响并等待确认。

## 可直接执行

- 单一页面或私有模块内的文案、布局、样式和无歧义缺陷修复。
- 使用现有 NativeWind 工具类，或在单一模块内迁移静态样式。
- 不改变行为、导出或数据结构的局部重构。
- 运行只读检查、格式检查、类型检查、Lint 和构建验证。
- 修正与当前配置明显不一致的文档事实。

## 必须先确认

### 业务与接口

- 登录流程、权限、角色、路由可达性、重定向、菜单和深链接。
- API 地址、请求响应字段、鉴权、错误语义、重试、缓存和持久化。
- mock 数据改为真实数据，或改变既有默认值、数据模型和用户操作结果。

### 公共结构与配置

- 新增或替换导航、状态管理、请求、图表、缓存等基础设施。
- 修改 `app.json`、应用权限、bundle identifier、图标、启动图或平台行为。
- 升级 Expo、React Native、NativeWind、Tailwind 或其他关键依赖。
- 修改全局 CSS、Tailwind preset、全局设计令牌或公共组件职责。

### 范围与交付

- 大规模删除标准 Expo 模板遗留文件、批量重命名或目录迁移。
- Git 提交、推送、分支、合并、发布及其他外部状态变更。
- 存在两种以上会显著改变产品体验或维护边界的合理方案。

## 精简优先与代码洁癖规则

### 项目协作偏好

- 每次改代码先检查哪些代码可以删除，再判断哪些代码必须修改，最后才考虑是否需要新增代码。
- 优先采用简单、直接、可读的实现；不要为了形式统一制造更长的调用链或无实际复用价值的抽象。
- 只有一个明确调用方的逻辑，默认留在当前文件或当前 feature 中；不要为了抽象而新增平行 helper、工具文件或中转层。
- 修改前先查真实调用方、返回值消费方、路由边界、权限边界、请求边界和持久化边界；不能只按文件名或方法名判断职责。
- 优先删除无业务价值的透传、换名包装、重复校验、重复转换和“左手倒右手”代码；保留认证、权限、错误归一化、请求取消、跨端隔离等真实边界。
- 未得到明确要求时，不主动扩大改动范围，不顺手重构无关模块。

### 极简代码规则

- 在功能、权限、安全、性能和可读性不下降的前提下，默认追求改动后的代码总量减少。新增代码必须说明为什么不能通过删除、内联、复用或合并解决。
- 能内联就不抽 helper，能复用就不复制，能合并分支就不保留平行路径，能让调用方直接完成就不增加中转层。
- 发现死代码、旧兼容分支、无效默认值、重复转换、重复校验、无意义类型包装、只调用一次的私有方法或未使用字段时，优先删除，不为“以后可能用到”保留空间。
- 不为了少几行代码写出难读的嵌套表达式、隐式副作用、过宽类型或职责混杂的方法；代码短必须同时保持意图清楚、边界明确、错误可追踪。
- 如果实现后代码量增加，交付说明必须列出新增代码承担的真实职责，以及删除、内联或合并了哪些冗余路径；没有明确职责的新增代码视为不合格。
- 写新代码前必须使用 `rg`、调用方检索和同层横向对比查找已有实现，不能只搜索同名函数；已有语义相同或可扩展的代码必须复用或直接修改。
- 不新增只做参数改名、简单透传、原样包装返回值、换个函数名继续调用另一个函数的“左手倒右手”方法。
- 不新建同义平行文件，例如已有 `xxxApi.ts`、`xxxClient.ts` 或 `xxxUtils.ts` 时，不随手新增 `xxxHelper.ts`、`xxxCommon.ts` 或 `xxxV2.ts`。
- 至少有两个稳定调用方，或者能够隔离明确复杂性时，才考虑抽取公共组件、hook、工具或跨 feature 模块；单一调用方默认留在原处。
- 抽象必须减少真实复杂度、消除稳定重复或隔离明确边界，不能只为了“统一”制造更长调用链。

### 移动端职责边界

- 路由文件只负责导航编排和页面级守卫；页面展示与局部交互留在 `src/screens/`。
- feature 负责对应业务的数据请求、类型和异步状态；不要为一次调用新增一层无行为变化的请求包装。
- `src/components/` 只放跨页面稳定复用的组件；单页面组件默认放在所属 screen 附近。
- 只有多个业务 feature 共同消费的稳定契约，才考虑放入公共模块；不要为了“单一来源”提前建立通用基础设施。
- 新增请求、鉴权、缓存、持久化或全局状态前，必须确认它确实承担请求边界、错误边界、生命周期边界或跨页面状态职责。

优化目标是减少重复、降低复杂度，不是制造更多文件。

## 确认请求

说明变更场景、受影响用户或文件、主要风险、推荐方案、替代方案及推荐理由。
